# 界面外观：Codex 风格深色主题（设计）

## 目标

界面此前用的是 Qt 原生控件外观（浅色、带立体感），与这个工具的气质不符，也不利于长时间
看报告与脚本。目标：**照 Codex 桌面版的外观做一套深色主题**，让它看起来像同一类工具。

## 令牌来源（不凭印象调色）

从本机 Codex 桌面版的样式表里直接解出来的，路径：
`/opt/codex-desktop/resources/app.asar` → `webview/assets/app-*.css` → `electron-dark` 作用域。

| 用途 | Codex 原值 | 本项目令牌 |
| --- | --- | --- |
| 主背景 | `--gray-900` `#181818` | `bg` |
| 面板 / 编辑器 | `--gray-800` `#212121` | `bg_elevated` |
| 更深一层（只读底、凹陷） | `--gray-1000` `#0d0d0d` | `bg_under` |
| 文字 主 / 次 / 三级 | `#fff` / 70% 白 / 50% 白 | `fg` / `fg_secondary` / `fg_tertiary` |
| 边框 浅 / 常规 / 重 | 4% / 8% / 16% 白 | `border_light` / `border` / `border_heavy` |
| 焦点描边 | `#339cffb3` | `border_focus` |
| 强调 / 成功 / 警告 / 错误 | `#339cff` / `#40c977` / `#fb6a22` / `#ff6764` | `accent` / `ok` / `warn` / `error` |
| 圆角 | 6px / 8px / 胶囊 | `radius` / `radius_lg` |
| 列表行高 | 30px | `row_height` |

## 设计要点

1. **颜色只有一个出口**：`ui/theme.py` 的 `css()`（QSS 用）与 `qcolor()`（QPainter/QPalette 用）。
   界面代码不许再写颜色字面量 —— 深色底上出现浅色残留，几乎都是某处写死了颜色。
2. **去原生感**：改用 Fusion 样式（原生样式自带的立体感不受调色板控制）；按钮不用渐变/阴影，
   只叠一层白表示 hover/按下；圆角统一 6/8px；页签做成胶囊；列表行高 30、无网格线；
   分割器是 1px 细线；滚动条细条、轨道透明。
3. **字体分工与 Codex 一致**：界面文字用系统 sans，**脚本、报告、输出、diff 用等宽** ——
   这些内容是用来核对的，等宽才看得清列对齐与空格。
4. **语义色跟着主题走**：阻断/错误用 `#ff6764`、通过用 `#40c977`、未跑/非阻断用灰
   （`#afafaf`）。diff 的浅绿/浅粉底在 `#181818` 上会变成刺眼色块，改成低饱和深底 + 亮前景。
5. **栏头**：三栏各一行"小号、次级色、字距略宽"的标题（方案与模板 / 脚本与轮次 / 校验与输出）。
   分区感靠栏头与 1px 细线，不靠边框和凹陷。
6. **主操作**：底栏"开始"用白底黑字（Codex 的主按钮约定），其余按钮是 5% 白叠加 + 1px 边框。

## 必须记住的一个坑（已写成测试）

**Qt 把 8 位 hex 解析成 `#AARRGGBB`，不是 CSS 的 `#RRGGBBAA`。** 于是 Codex 的
`#ffffff0a`（4% 白）在 Qt 里是"不透明的黄"，实测渲染成 `#ffff0a`。这个错误 QSS 不报错、
palette 也不报错，界面就是花的 —— 只有截图取色才看得见（本次就是取色抓出来的）。
所以：半透明颜色一律写成 `(r,g,b,a)` 元组，经 `css()` / `qcolor()` 出口使用。

## 验证方式

`tests/test_theme.py` 两层断言：
- 字符串层：样式表里不许出现 8 位 hex；关键令牌与 Codex 原值一致；
- 像素层：离屏画一遍主窗口，对主背景、只读区、主按钮**取色**（`#181818` / `#0d0d0d` / `#ffffff`）。

两个变异体（把半透明令牌改回 8 位 hex、不装主题）都能让对应用例转红。

## 范围外

- 亮色主题、跟随系统切换：本次不做。
- 布局重构（顶部标题栏、左侧导航、右侧检查器）：本次不动骨架，保持已被测试锁住的三栏结构。
- 图标、动效、字体打包（等宽字体仍是"探测本机可用族"，找不到就退回 monospace）。


## 修订（2026-09-19，用户反馈后）

用户看完第一版提了两点：**"颜色尽量显得高级，尽量圆角"**、**"缩放有问题，不能调节竖向的长度"**。

### 1. 色板精修（不再是 Codex 原值）

照抄的是 Codex 的**结构与比例**（分层关系、字号、行高、三级文字），色值改成有意精修：

| 令牌 | 第一版（= Codex） | 现在 | 为什么 |
| --- | --- | --- | --- |
| `bg` | `#181818` | `#101114` | 冷调更深；"高级感"来自低对比分层，不是把面板刷亮 |
| `bg_elevated` | `#212121` | `#17181c` | 面板只比底色亮一档 |
| `bg_under` | `#0d0d0d` | `#0b0c0e` | 只读底再深一档 |
| `fg` | `#ffffff` | `#ecedf0` | 纯白在高对比深底上偏刺眼/廉价 |
| `accent` | `#339cff` | `#7c9cff` | 偏靛蓝，比"互联网蓝"收敛 |
| `error` | `#ff6764` | `#f2707a` | 语义色降饱和，红色留给真问题 |
| `radius` / `radius_lg` | 6px / 8px | **10px / 14px** | "尽量圆角"；页签改胶囊 |

三栏与底栏各是一张"卡片"（`QWidget#paneCard`：大圆角 + 极淡边框）—— 圆角要看得出来就得有
边框，而栏与栏的分隔感也由它提供（分割条平时透明，只在悬停/拖动时显色）。

### 2. 缩放：两个真实缺陷

- **分割条抓不住**：第一版把 `QSplitter::handle` 的宽/高写成 1px，视觉上像 Codex 的细线，
  但鼠标抓不住。现在用 `setHandleWidth(8)` 在**代码里**设死（不能只靠 QSS：样式表没加载时
  会退回 Qt 默认的 4px，而"能不能用鼠标操作"这种属性不该依赖样式表）。
- **上下两块比例不可调**：三栏区与"历史+设置"区原本是 `QVBoxLayout` 的 1:1，根本不是分割器，
  怎么拖都不可能变。现在改成"上下竖向分割器 + 历史/设置横向分割器"，四个分割器都能拖。
- 另外各栏内部控件的 `minimumSizeHint` 加起来有 400~500px，会**锁死**分割器比例（拖了没反应），
  所以给每块设了可接受的最小高度（140~200px），压小了靠滚动条看。
- **尺寸记忆**：拖完写进设置（`AppSettings.layout`，可读的 JSON 尺寸而非 `saveState()` 字节），
  下次开窗还原。还原必须放在 `showEvent` 里 —— 控件没显示前几何尺寸未定，构造期 `setSizes()`
  会被夹成平均分布（实测：构造期设 `[397,649]`，显示后变 `[238,238]`）。

### 3. 这一轮新增的测试（都做了变异验证）

`tests/test_ui_layout.py`：所有分割器把手 ≥6px、上下能拖（压得下去/顶得上来）、尺寸存得进
设置且还原、坏掉的布局串不致命、把手宽度不依赖样式表；`tests/test_theme.py` 增加"圆角真的画出来了"
（取角落与中心两个像素比较：角落应露出父底色）。


## 修订二（2026-09-19）：缩小窗口时内容被压没

用户反馈："当我缩小窗口的时候，里面的栏目也跟着挤压了，最后会挤压到看不见。"

实测复现（离屏，窗口高 560px）：

| 控件 | 900px 高时 | 560px 高时 |
| --- | --- | --- |
| 方案预览 | 58 | **12** |
| 右栏报告树 | 171 | **35** |
| 右栏输出区 | 171 | **35** |
| 轮次时间线 | 174 | 60 |

根因：这些内部控件**没有最小高度**，QVBoxLayout 会把它们一路压到近零（固定高度的控件，
比如 64px 的补充要求框，反而不受影响 —— 所以越挤越不均匀）。

修法两条：
1. **关键内部控件声明最小高度**：方案预览 90、脚本/diff 视图 140、时间线 80、对话记录 120、
   报告树 110、输出 110、notes 80、历史列表 90、历史详情 60。
2. **栏与窗口声明最小尺寸**：每栏最小宽度 240~300、最小高度 220~260；窗口最小 960×700
   （= 三栏最小宽 + 两条 8px 把手 + 边距）。低于这个尺寸这个界面本来就放不下，与其让 Qt 把内容
   裁掉，不如让窗口管理器直接不许缩到那么小 —— 平铺窗口管理器也会读 min-size 提示。

修完实测：窗口缩到 960×700 时，方案预览 90、报告树 110、输出 110、脚本 299、历史 90，
没有一块被压没。测试里加了三条（窗口最小尺寸、控件最小高度声明、下限尺寸下内容仍可见），
两个变异体（撤掉预览的最小高度、撤掉窗口最小尺寸）都能转红。

**仍然存在的边界**（诚实写明）：平铺窗口管理器如果无视 min-size 提示、强行把窗口压到更小，
Qt 只能**裁切**（内容被切掉一部分）而不是继续压扁。要彻底解决得把每栏内容包进滚动区域，
本轮没做 —— 因为那会改变三栏"填满窗口"的手感，收益不明显。


## 修订三（2026-09-19）：排布重做 —— 底部「工具区」页签 + 可折叠区块

用户反馈："有些地方如果尺寸太小是否可以增加折叠起来呢，或者你的排布需要重新修改一下……
可以把有些栏目放到环境自检和设置这一横行，用按钮点开进行修改，这样可以节省空间。"
裁定结果：**方案 A（只做底部工具区页签）+ 折叠默认展开可记忆**。

### 新排布

```
┌──────────┬───────────────┬───────────────┐
│ 方案与     │ 脚本与轮次     │ 校验与输出     │   ← 主区三栏，各只干一件事
│ 运行参数   │ （本轮/对比）  │ 报告/输出/取舍 │
├──────────┴───────────────┴───────────────┤
│ [历史运行][模板库][模型对话][环境自检][设置] │   ← 工具区（原 sidePages 演进）
├──────────────────────────────────────────┤
│ 开始 取消 继续修复 改后重跑 │ 状态文字        │
└──────────────────────────────────────────┘
```

- `sidePages`（环境自检/设置两页）→ **`toolTabs`**：历史运行 / 模板库 / 模型对话 / 环境自检 / 设置。
- `templatesPane` 从左列**移进工具区**；左列不再上下堆两块，改叫「方案与运行参数」。
- 模型对话从中栏第三个页签**移进工具区**（`MainWindow.chat_panel`）。
- 右栏三块（校验报告 / 执行输出 / 模型取舍说明与假设）各自包进 `CollapsibleSection`：
  **默认展开**，点标题行收起，状态写进 `AppSettings.collapsed_sections` 并还原。
- 分割器从四个变成三个（main / vertical / center），布局记忆的键同步更新。

### 过程中发现并修掉的两个真问题

1. **工具区最小高度装不下最高的页签**：实测对话面板 `minimumSizeHint` 305px，而工具区最小
   只有 200px —— 内容溢出被裁，症状是输入框盖在记录区上。改成工具区最小 300px、窗口最小
   960×780（高度下限按"最高的常看页签装得下"定）。测试 `test_tool_area_is_tall_enough_for_its_tallest_tab` 守着。
2. **`QPlainTextEdit:read-only` 在页签里不再稳定命中**：对话记录区（只读）渲染成了输入框的底色。
   改成对 `#chatTranscript` **显式**指定更深的只读底 —— "只读区看起来和输入框一样"会让人
   以为可以直接在里面打字。

另外：取色验证改了两处方法。一是**先切到目标页签**再取色（未选中的页签不渲染）；
二是对页签内的控件改用**控件自己的帧**（`widget.grab()`），因为整窗帧按坐标取色会被页签裁切
与相邻控件遮挡影响 —— 这条用例第一版就是被这两点坑了两次。


## 修订四（2026-09-19）：页签的圆角原来根本没生效

用户指出："工作区这里，历史运行、模板库、模型对话等等，这几个按钮不是圆角的。"

**根因**：Qt 画页签时，**圆角半径 >= 页签高度的一半就整个退回画直角**。我按 CSS 习惯写的
`border-radius: 999px`（"胶囊"写法）在这里不是"更大的圆角"，而是**完全没有圆角**。

实测（页签高 28px）：

| 半径 | 8 | 10 | 12 | 14 | 16 | 17 | 20 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 是否圆角 | ✅ | ✅ | ✅ | ✅ | ❌ | ❌ | ❌ |

修法：`radius_pill` 从 `999px` 改成 **11px**（页签高 24~34px 时都安全），页签最小高度提到
24px。工具区与中栏的页签栏都跟着生效。

**为什么测试没发现**：原来的主题测试只断言 QSS 字符串里有 `border-radius`、以及面板/按钮/
只读区的渲染色 —— 页签这条从来没取过色。现在加了 `test_tab_corners_are_actually_rounded`：
拿**选中的**页签（只有它有填充色），比较它的左上角像素与填充色，相同就是直角。
把 `radius_pill` 改回 `999px` 这条用例会立刻转红。

**教训（写下来别再犯）**：凡是"画出来才知道对不对"的样式，都要有一条取色断言；
字符串层面正确的 QSS 可能在 Qt 里被静默忽略。


## 修订五（2026-09-19）：输入控件的底色是矩形 —— 三个叠在一起的原因

用户指出："虽然按钮是圆角，但是按钮底色还是长方形的。"

排查过程（每一步都有取色证据）：

1. **先排除了页签与按钮**：把像素降采样成字符图后，选中页签与主/次按钮的填充在上下边缘都
   明显收窄 → 它们是圆的。审计脚本（遍历所有控件、比较四角与中心）列出真正是"矩形填充"的
   是输入类：`QComboBox`(263×13)、`QSpinBox`(263×13)、`QPlainTextEdit`。
2. **控件被压扁**：左栏内容需要 576px（最小 474），实际只分到 383px → 表单把下拉/微调框压到
   **13px 高**（sizeHint 29px）。而 13px 高时圆角半径 10px ≥ 半高 6.5px，
   **Qt 会整个退回画直角**（和页签那次是同一条规则）。
3. **输入框与面板同色**：输入底 `#17181c` == 卡片底 `#17181c`，所以圆角处的像素与填充同色 ——
   即使真画了圆角也看不出来。

三处一起修：

| 修法 | 内容 |
| --- | --- |
| 表单可滚动 | 新增 `widgets/scroll.py`，左栏 / 模板库 / 设置页 / 自检页的**表单进滚动区**：空间不够时滚动，而不是压缩控件（`test_left_pane_scrolls_instead_of_clipping_when_short` 守着） |
| 输入更深 | `bg_input` `#17181c` → `#121317`（比卡片深一档，圆角才立得住；`test_input_surface_differs_from_the_panel_so_rounding_is_visible` 守着） |
| 圆角验证 | 新增隔离窗口测试：五种控件（下拉/微调/单行/多行/按钮）在正常高度下角像素必须 ≠ 填充色 |

**一个被撤掉的改动（记下来）**：中途给单行输入加过 QSS `min-height: 24px` 防压扁，但变异测试
证明"撤掉它测试照样全绿" —— 因为容器小于最小尺寸时 Qt 反正会挤压，真正管用的是滚动区 +
窗口/栏目的最小尺寸。而且 QSS 的 `min-height` 会**覆盖** `setMinimumHeight()`（实测把方案预览
的下限从 90 冲成 34）。所以这条规则被删掉，不留"看着有用、其实没有"的样式。

另外，取色验证在这轮被坑了两次，方法也修了：**滚动区裁切**会让 `mapTo()` 的坐标落到别的控件上
（取色取错对象），以及 **`widget.grab()`** 对被滚出视野的控件会返回空白帧。现在凡是输入类的
圆角与底色，都在**隔离窗口**里验证。


## 修订六（2026-09-19）：右栏折叠改为按可用高度自动判定

用户裁定："这里如果尺寸足够就不用折叠，这里不需要手动去折叠，请你根据尺寸自动判断是否需要折叠。"

改法：删掉"点击标题手动切换 + 状态写进设置"那一套，改成**纯自动**：

- 优先级固定 **校验报告 > 执行输出 > 模型取舍说明与假设**。理由：运行中盯着的是"有没有问题、
  跑成什么样"；取舍说明是事后核对方案约束时才看的，空间不足时它先让位。**校验报告永不自动收起**。
- 判定逻辑抽成纯函数 `plan_collapse(available, minimums, keep_expanded)`（好测），
  在 `RightPane.resizeEvent` 里执行；带 16px 缓冲带，拖分割条时不会在边界上抖。
- 标题行从 `QToolButton` 换成 `QLabel`：它只显示状态（▾/▸）与原因（tooltip），不再接收点击 ——
  可点的标题会让人以为"这里要手动操作"。
- `AppSettings.collapsed_sections` 字段随之删除（不再持久化折叠状态）。

实测（真实操作触发，右栏高度 → 自动收起）：

| 右栏高 | 自动收起 |
| --- | --- |
| 484px | 无 |
| 370px（窗口缩到最小） | 模型取舍说明与假设 |
| 260px（再拖竖向分割条） | 执行输出 + 模型取舍说明与假设 |
| 拖回大尺寸 | 自动展开回来 |

测试用**真实操作**（缩窗口 + 拖竖向分割条）触发，不直接改控件尺寸 —— 右栏挂在布局里，
直接 `resize()` 会被布局覆盖（这条测试第一版就是这么失败的）。三个变异体（永不自动收、
优先级反了、只收不展开）都能转红。

**操作教训**：回滚变异体时我用了 `git checkout <file>`，把该文件里**未提交**的正经改动一起
回滚了（right.py）。变异体一律用 `cp` 备份/恢复，不用 git checkout。

设置页新增「外观」分组，四个字段（都存在 `AppSettings` 里、随设置文件持久化）：

| 设置 | 字段 | 行为 |
| --- | --- | --- |
| 界面缩放 | `ui_scale`（0.8–1.6，默认 1.0） | **同时**放大字号与所有尺寸（圆角、行高、内边距、滚动条宽度、栏头字号）。只放大字号会让界面变挤。颜色不缩放。 |

| 背景效果 | `backdrop`（off / translucent / blur） | 见下。 |

### 亚克力模糊：能做与不能做，都写清楚

**真正被模糊的是窗口背后的内容**，这只有窗口管理器/合成器能做，Qt 没有跨平台接口。所以分两步：

1. **半透明**（任何平台都能做）：`WA_TranslucentBackground` + 底色带 alpha（面板 92%、只读底 82%）。
   文字与强调色**不做透明**——那会直接毁掉对比度（测试里锁住了这一条）。
2. **模糊**（能拿到才做，`ui/backdrop.py`）：
   - Windows 11 22H2+：`DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE=38, 3=Acrylic)`，
     顺带 `DWMWA_USE_IMMERSIVE_DARK_MODE` 把标题栏也切深色；
   - KDE/X11：`_KDE_NET_WM_BLUR_BEHIND_REGION`（本环境没有 xcb 绑定 → 如实返回 False，
     不去 shell 调 xprop，免得在用户机器上留下莫名其妙的子进程）；
   - Wayland（Niri/sway/GNOME）：**没有给普通应用的模糊接口** → False；
   - macOS：NSVisualEffectView，本 PySide6 环境不支持 → False。

拿不到模糊时**不假装成功**：`blur_available=False`，状态栏与设置页如实写"当前桌面不支持窗口
模糊，已退化为半透明"。这条断言是**对着平台的真实能力**比的（直接调 `try_enable_blur`），
而不是对着窗口自己报的标志——第一版就是拿标志当基准，于是"把标志写死成 True"这个变异体照样通过。

具体到这台机器（Arch + Niri/Wayland）：**模糊拿不到，只能半透明**。Windows 上应当能拿到真正的亚克力。

### 热更新

`MainWindow.apply_appearance()` 统一负责装主题 + 窗口半透明 + 平台模糊；生产入口 `app.py` 在建窗口
后调它，设置保存后 `_on_settings_saved` 也会调它 —— 改缩放/字体/背景**不需要重启**。

### 测试（三个变异体都能转红）

`tests/test_appearance.py`：缩放同时改字号与尺寸（含**像素级**"按钮真的变高了"）、默认缩放不改版式、
字体落到样式表、默认背景完全不透明、半透明时底色带 alpha 且**文字仍不透明**、模糊可用性不谎报、
四个字段存取往返。变异体：缩放只改字号 / 默认改半透明 / 谎报模糊可用 —— 分别让对应用例转红。


### 性能事故（记下来）：设置页的字体下拉把测试从 47s 拖到 332s

加完外观设置后整套测试从 47s 涨到 **332s**。定位过程：

1. 先怀疑字体枚举 → 加进程级缓存 `@lru_cache` 的 `font_families()`：**没用**（27.3s → 27.4s）。
2. 再怀疑 `setStyleSheet` 重新 polish 所有窗口 → 给 `apply_theme` 加**幂等短路**（内容相同就不设）：
   **也没用**。
3. 用 `--durations` 看每条用例：单条 1.6~4.3s，说明代价在"建一次窗口"这条路径上。
4. 真凶：设置页构造时给两个下拉各插入 **2106 个字族**（4200+ 次 `addItem`），而每个 MainWindow
   都会建一个设置页。

修法：字体列表**延迟到设置页真正显示时才填**（它平时躲在工具区页签里，根本不需要）。
效果：外观测试 27.4s → **6.4s**，整套 332s → **60s**。

顺带保留的两处改动（各自独立成立，不是这次的主因）：字族按进程缓存、`apply_theme` 幂等短路
（后者对生产也有意义：切页签/重建窗口时不必重新 polish 整棵树）。


## 修订九（2026-09-19）：半透明的真正拦路虎是**层数**，不是 alpha

用户连着两轮反馈"主工作区的黑底与浅黑底没有透明效果""还是没有完全透明，对话框之类的还是纯黑底
和浅黑底"。前两轮我都在调 alpha（92% → 78% → 窗口 43%），都没解决 —— 因为问题不在单层透明度。

### 怎么测出真相："双背景法"

把界面分别渲染到**品红**与**纯绿**两张画布上，同一像素的红通道差值为 `(1-α)·255`
（表面自身颜色被消掉，剩下的就是真实合成不透明度）。于是得到一张"等效不透明度图"：

- 探针脚本先量到主工作区 **95~97%**，而窗口空白处只有 43%（= 窗口 CSS 的 alpha）——
  说明内容区下面还压着别的东西；
- 再逐层量**祖先链自身的底色**，抓到真凶：`QSplitter → QStackedWidget → QTabWidget →
  折叠区块 → 容器 QWidget` 每一个都在重刷一遍窗口底色。**43% 叠四到六层 = 97%**。

### 三处修法（缺一不可）

1. **容器一律不上色**：QSS 里给 `QSplitter / QStackedWidget / QScrollArea / QTabWidget::pane /
   CollapsibleSection / #sectionBody / 各页签页` 写 `background: transparent`，底色只在最外层画一次。
2. **调色板不重复着色**：`build_palette` 在半透明模式下把 `Window / Base / AlternateBase /
   Button / ToolTipBase` 置为全透明（QSS 已经上过色，调色板再来一遍就是两层）。
3. **视口不重复着色**：Qt 给 `QAbstractScrollArea` 设了 QSS 底色后，视口会再画同一层
   （实测 51% 被叠成 74%），`unstack_viewports()` 把视口底色交还外层。

另外两个被同一病根连累的地方：`thin_containers()` 连容器的调色板也清掉；
**对话框是独立顶层窗口**，`WA_TranslucentBackground` 只设在主窗口上时，弹出的确认框仍是一整块
纯不透明深色 —— 现在 `backdrop.apply_to()` 统一处理主窗口与所有对话框，确认框在构造末尾调用它。

### 修完的实测值（双背景法，等效不透明度）

| 区域 | 修前 | 修后 |
| --- | --- | --- |
| 窗口空白处 | 43% | **43%** |
| 方案预览 | 96% | **46%** |
| 对话记录 | 87% | **61%** |
| 脚本 / 输出 / 报告视图 | 95~97% | **71%** |

内容区保留约七成不透明是**刻意的**：那里是等宽代码与诊断报告，全透会让文字糊在壁纸上。
空白与卡片区域透出一半以上，观感上"透"是明确成立的。

测试：`test_rendered_surfaces_let_the_backdrop_through`（整窗渲染 + 坐标映射取样，
断言每个表面至少透出 18%、至多 75%）、`test_opaque_mode_keeps_every_surface_solid`
（off 模式不许被透出来）、`test_dialogs_follow_the_translucent_backdrop`
（对话框要带 `WA_TranslucentBackground`，关掉后新开的对话框要回到不透明）。


### 修订九补记：页签条那一条"方角底色"

用户圈出「工具区」的页签条：整条底色是直角矩形。实测原因 —— `QTabBar` 原来没写底色，
由调色板自绘（Fusion 风格填充 + 类框架），条内等效不透明度 **69%**、条外只有 46%，
所以它是一条比周围更实、更亮的方角块。改法：给 `QTabBar` 显式写 `background-color: bg_elevated`
与 `border-radius: radius_lg`，圆角就与下面的面板对得上（页签本身仍是胶囊）。

测试 `test_tab_strip_background_is_rounded`：条内取"页签上方的内边距"处的纯底色，
断言它是半透明的（不是调色板刷的不透明块）且与角落不同色。变异体验证：撤掉那条
`border-radius`，用例立刻转红。


## 修订十（2026-09-19）：亚克力模糊不必等系统支持 —— 自己模糊壁纸

用户问："亚克力模糊为什么要系统支持呢，不用系统支持你可不可以支持亚克力模糊？"

### 为什么"真亚克力"要系统支持

要模糊的是**窗口背后**的像素，而那些像素只有合成器拿得到（Windows 的 DWM、KWin、
Hyprland 的 blur 插件）。应用自己读不到别的窗口：Wayland 出于安全根本不允许，
X11 抓屏拿到的也是"整块屏幕"而不是"窗口背后"。

### 但观感可以自己造

壁纸图片是能读的，而窗口背后通常就是壁纸。于是新增 `ui/acrylic.py`：

1. **找壁纸**：设置里指定的（图片或目录）→ DankMaterialShell 的会话状态
   （`~/.local/state/DankMaterialShell/session.json` 的 `wallpaperPathDark`）→ KDE 的
   `appletsrc` → hyprpaper 配置 → `~/Pictures` 里最新的一张；
2. **模糊**：按半径大幅降采样再逐级放大（mipmap 式）。两个被否掉的做法：
   `QGraphicsBlurEffect` 在**离屏场景里不生效**（实测接缝处仍是纯黑，半径 40/80 都没变化）；
   在 Python 里做可分离卷积又太慢（百万级像素的循环）。现在的实现全程在 Qt 的 C++ 里，
   1400×900 实测 **0.07s**，结果按 (路径, mtime, 尺寸桶, 强度) 缓存，换壁纸/改强度才重算；
3. **铺到窗口最底层**：`MainWindow.paintEvent` 先画模糊壁纸，**再**让 QSS 的半透明深色底
   压上去 —— 顺序反了就是一张普通背景图，不是毛玻璃。尺寸变化时按新尺寸重算（分桶缓存）。

### 说清楚的代价（不假装它是真亚克力）

- 背后如果是别的窗口，它不会出现在这一层里 —— 这是静态壁纸，不是实时抓屏；
- Wayland 拿不到窗口的屏幕坐标，模糊层按窗口大小重新裁切，**不保证与桌面壁纸逐像素对齐**
  （模糊之后这点错位基本看不出来）；
- 找不到壁纸时退化为普通半透明，状态栏与设置页都如实写明白。

设置页新增两个旋钮：「亚克力壁纸」（留空 = 自动找，带"选择图片…"）与「模糊强度」（0~120 px），
背景效果下拉里新增「亚克力模糊（自绘壁纸，不需要系统支持）」，与原来那条
「亚克力模糊（问系统要，Windows 有）」并存 —— 两条路各自成立，谁都不冒充谁。

测试（`tests/test_acrylic.py`，9 条）：找壁纸的四种来源、目录取最新、找不到返回 None、
模糊真的把硬边摊开（而两端保持原色）、没有壁纸就退化为半透明并如实提示、切走模式要撤掉那一层、
两个字段存取与设置页回填。判据用的是"同一扇窗分别渲染到品红与纯绿画布"：亚克力下两张图必须
**逐像素相同**（壁纸层不透明），半透明下必须不同。


## 修订十一（2026-09-19）：浮层不参与透明化 —— "看不见字"的三种成因

用户反馈："选择亚克力模糊的时候，选择字体的背景也跟着透明了，看不见字"。

追下来其实是**三件不同的事**凑在了一起，每一件都得单独修：

### 1. 下拉弹层整块透明（主因）

实测：把界面渲染到品红/纯绿上反推，**设置页里的**下拉，其弹出列表底色与壁纸同色
（行底色 = 189，文字 236 → 对比度 **1.7:1**）；而独立的下拉却是正常的深色。
原因：弹层是独立顶层窗口，会继承页面的调色板（页面在透明模式下是 transparent）。
另外**真正要上色的是"弹层容器"那一层**（QComboBox 的 QFrame 弹窗），只给列表上色没用。

修法：`theme.py` 里加"浮层守卫"（`_PopupKeeper`）—— 在 `Polish/Show` 事件上把底色钉死，
并在 `apply_theme` 时对已存在的浮层先钉一遍；浮层单列令牌 `bg_menu`（非 off 模式 alpha 244 ≈ 96%）。
判据用"窗口类型字段"精确判断弹层：`Qt.WindowType.Popup` 的位里含 `Window`，
直接位与会把所有顶层窗口判成弹层（实测把主界面列表也染成浮层色，六个用例转红）。

### 2. 输入类表面不够不透明

收起状态的下拉（字体名就写在那里）在亮壁纸上的对比度只有 **3.1:1**（可读线 4.5:1）。
所以 `bg_input` 从 51% 提到 80%：输入框/下拉/数字框是读字与写字的地方，透明让给大块的只读内容区。
"内容区要明显透"那条用例相应改成断言输入类的**下限**。

### 3. 亚克力层本身太亮

真亚克力的配方是"模糊 + **色调** + 噪点"，我第一版只做了模糊：本机壁纸平均亮度 **189**，
浅色文字直接压上去当然糊。补上色调层（59% 深色），壁纸仍看得出来，字也压得住。

三处都有测试：`test_combo_popup_stays_readable_in_transparent_modes`（弹层在亮底上的对比度 ≥ 4.5:1，
撤掉守卫立刻转红）、`test_acrylic_layer_is_dark_enough_for_light_text`、
以及输入类 alpha 的下限断言。

## 修订十三（2026-09-19）：面板圆角外的"深黑色角"

用户圈出「校验与输出」栏里几处"深黑的色角"。用像素普查定位，**不是圆角没生效**，
而是有两层东西在圆角外面露出了既不属于面板、也不属于它背后那层的颜色：

1. **纯容器在画窗口底色**：折叠区块的外壳与 `#sectionBody` 这类纯布局容器被 Qt 标了
   `WA_StyledBackground`；`不透明` 模式下没有对应 QSS 规则时，Qt 用调色板的 Window 色

   修法：`CollapsibleSection, #sectionBody { background: transparent }` **在所有模式下生效**
   （之前这条规则只在半透明模式下启用）。
2. **表头 `::section` 自带底色**：`QHeaderView::section` 写的是窗口底色，而表头是列表/树的
   **子控件，不会被父控件的圆角裁剪** —— 校验报告树的左上/右上角因此露出深色方块。
   修法：`QHeaderView, QHeaderView QWidget { background: transparent }` 且 `::section` 改为透明，
   底色交给下面的圆角面板自己显示（只保留底部分隔线）。

### 判据（通用，不针对某一处）

`test_no_rounded_panel_shows_foreign_colors_at_its_corners`：把整窗渲染出来，对十个圆角面板

## 修订十五（2026-09-19）：重影、合并亚克力选项、文案再收一遍

用户反馈三件事："半透明又成这种重影的了"、"系统提供和界面自绘没有区别了"、
"不要出现『生成脚本用』的文字，不要口语化"。

### 1. 重影 = 半透明窗口没有擦除重绘区域

半透明窗口（`WA_TranslucentBackground`）的底色带 alpha，正常绘制是**混合**而不是**覆盖**：
滚动或重排后只重绘一块区域时，上一次留在后备存储里的像素会透过来 —— 屏幕上就是重影。
实测：把窗口渲染一次，滚动 40px 后**只重绘滚动区**，与"全新渲染"相比有 6 万多个采样点不同。

修法两条一起用：

- `backdrop.erase_damage(widget, event)`：在 `paintEvent` 里先把这次要重绘的区域用
  `CompositionMode_Source`（替换，不受 alpha 影响）擦成透明，再走正常绘制；
  **画完必须 `painter.restore()`** —— 合成模式是画笔状态，留在 Source 上会让后续所有绘制
  都变成"替换"，半透明整体失效（实测：留在 Source 上时窗口渲染不再与背景混合）；
- 任何滚动条一动就 `window.update()`（`_wire_scroll_repaints`）：整窗重绘 + 上面的擦除，
  才能保证那块区域回到"全新绘制"的样子。

顺带一个测量方法上的教训："品红/绿双画布"那套反推 alpha 的办法**被擦除破坏了**（画布颜色会被
一并擦掉，两种底色渲染结果永远相同）。改用**渲染到透明画布直接读 alpha** —— 更直接也更准。

### 2. 合并两个亚克力选项

用户说得对：在拿不到系统模糊的机器上，"系统提供"与"界面自绘"完全一样，那是冗余。
现在只有三种背景效果：**不透明 / 半透明 / 亚克力模糊**；亚克力的模糊来源**按可用性自动选择**：
系统合成器（Windows 11 22H2+ 的 DWM）→ 界面自绘 → 半透明。老设置里的 `blur` 在读取时
归一到 `acrylic`（`AppSettings.normalize()`，`load()` 也要调 —— 直接 setattr 会绕过
`__post_init__`，第一版就漏在这里）。

另外补上：亚克力模式下**连壁纸都没有**时，生效模式退化为 `translucent`（重新打开窗口半透明），
而不是留一块不透明的深色。

### 3. 文案

- 设置页那一栏改为：分组「脚本生成」/ 行名「模型」/ 说明"用于生成 shell 脚本；
  模型对话的模型在「模型对话」面板中单独设置……"（"生成脚本用"这种以"用"结尾的口语标签删除）；
- 同一批清扫：对话面板占位与状态文字（"输入问题，例如：……"、"本对话使用的模型：……"、
  "当前会话：……"）、"上一条提问尚未返回"、"该目录未记录会话，无法恢复"等；

## 修订十六（2026-09-19）："半透明没有透明效果" —— 属性设晚了

用户报："你这半透明都没有透明效果了啊"。渲染层面量不出问题（透明模式的合成 alpha 是正常的
110~187），所以问题在**真实窗口**上：`WA_TranslucentBackground` **必须在窗口被创建之前设好**，
窗口已经在屏幕上时再改这个属性不会生效 —— Qt 的窗口后端早已定型。

而合并亚克力选项时我把亚克力改成了"窗口不透明"（当时是为了绕开浮层继承透明度的问题）。
于是用户的设置被归一成 acrylic → 启动时创建的是**不透明窗口** → 在界面上切回「半透明」时
属性虽然设上了，窗口却还是不透的 ✓ 症状与用户描述完全一致。

三处改动：

1. `_set_translucent(window, want)`：属性真的需要变、且窗口已经在屏幕上时，**隐藏再显示一次**，
   强制按新属性重建窗口（Qt 的标准绕法）。下次显示前设属性的常规路径不受影响。
2. 亚克力也保持**半透明窗口**：自绘那层模糊壁纸本来就不透明、铺上就看不到桌面，所以观感不变，
   但「半透明 ↔ 亚克力」互切不再需要重建窗口。浮层可读性早就由 `_PopupKeeper` 单独钉住，
   不再依赖"窗口不透明"这个前提。
3. `erase_damage` 从"擦成透明"改为"**重填窗口底色**"：填透明会把 Qt 在 paintEvent 之前画好的
   窗口底色一并抹掉，边角处就成了没有背景的窟窿。填自己的底色既清掉了旧像素，也不会挖洞。

用例：`test_switching_background_modes_actually_toggles_window_translucency`（逐个模式断言窗口
属性与可见性，并断言切回半透明后自绘层已撤）。全套 343 passed / 1 skipped。


## 修订十七（2026-09-19）：Windows 上两个"透明"效果都不生效 —— 改成界面自绘

用户报："半透明和亚克力模糊在 win11 上都没生效"。查证后是**两条系统能力在真机上都不成立**：

1. **Windows 的 `WA_TranslucentBackground` 必须搭配无边框窗口**才生效
   （Qt 的已知限制；[StackOverflow 上这个问题](https://stackoverflow.com/questions/75432262/how-to-make-wa-translucentbackground-work-on-windows-without-using-framelesswindo)
   的答案是 Windows 上做不到）。我们保留原生标题栏 → 客户区永远不透明。
2. **Windows 11 的 DWM 亚克力要求窗口没有重定向位图**（`WS_EX_NOREDIRECTIONBITMAP`）——
   [VLC 的提交](https://mailman.videolan.org/pipermail/vlc-commits/2025-January/070907.html)
   正是为这个改的。Qt 的普通窗口有重定向位图，所以 `DwmSetWindowAttribute` 即使返回成功，
   那层背景也显示不出来。

于是**改成两端统一的自绘底色**，不再问系统：

| 模式 | 底色层 |
| --- | --- |
| 不透明 | 无（主题纯色） |
| 半透明 | 壁纸**不模糊** + 淡色调 `TRANSLUCENT_TINT`(alpha 96) |
| 亚克力模糊 | 壁纸**高斯模糊**（强度可调） + 浓色调 `TINT`(alpha 150) |

- 窗口**始终不透明**：`backdrop.py` 里删掉了 `enable/disable_translucent`、
  `try_enable_blur`、`_enable_windows_acrylic`、`_enable_kde_blur`（都成了不可达代码），
  文件顶部写清了为什么；
- 没有壁纸 → 生效模式退回 `off`（纯色）并如实说明，不留一块假的透明；
- `erase_damage` 填的必须是**不透明**色：窗口不透明之后，填带 alpha 的色会在重绘处挖出窟窿；
- `_window_background_color()` 有底色层时返回色调色，纯色模式返回主题底色。

连带的测量方法变化：窗口不再透明，"渲染到透明画布量 alpha"这套判据失效（永远 255）。
新判据是**颜色差异**：半透明模式下同一位置的颜色必须与纯色模式明显不同（壁纸透出来了），
以及**模糊程度差异**：用硬边壁纸时亚克力的过渡像素必须显著多于半透明。

用例：`test_backdrop_modes_paint_a_self_drawn_layer`、
`test_no_wallpaper_falls_back_to_a_solid_background`、
`test_translucent_is_sharp_and_acrylic_is_blurred`、
`test_rendered_surfaces_let_the_backdrop_through`（改判据）、
`test_switching_background_modes_switches_the_layer`、`test_dialogs_follow_the_current_backdrop_mode`。
整套 347 passed / 1 skipped。

## 修订十九（2026-09-20）：用「150% 缩放」模拟 Windows 形状，揪出一条真 bug

用户睡觉前的要求是"确保 windows 版本无误"。开发机是 Linux，真机行为没法直接验，
所以能做的就是**把 Windows 的形状在本机复现出来**，再让用例去撞。

### 复现手段

`QT_SCALE_FACTOR=1.5`（或 2）跑同一套用例：逻辑屏幕像素会按比例缩小
（offscreen 测试屏 800x800 → 150% 下只有 533x533），凡是"按屏幕可用区收敛"的规则
都会走进小屏分支 —— 这正是 Windows 150% 缩放（1080p 只有 720 逻辑像素高）的形状。

### 撞出来的真 bug：最小尺寸可以比屏幕还大

`window_minimum_for()` 里那个"舒适下限"是 `max(720, …)`，屏幕更小时它照样返回 720：

| 屏幕可用区 | 旧公式 | 新规则 |
| --- | --- | --- |
| 1920×1080 | 960×780 | 960×780（不变） |
| 1280×720（1080p/150%，用户机） | 960×612 | 960×612（不变） |
| 800×800（本机测试屏） | 720×680 | 720×680（不变） |
| 533×533（150% 模拟） | **720×520（比屏幕还大）** | 506×506 |
| 640×480 | **720×520（比屏幕还大）** | 608×456 |

"最小尺寸比屏幕还大"正是用户报过的那三条症状的根因：窗口管理器照给最小尺寸，
布局只能违反它 —— 文字出框、面板与输入框重叠、某栏被压没。
新规则：下限只在屏幕装得下时生效，否则收敛到可用区的九五成（宽 758 / 高 547 以下才触发，
所以大屏与用户机的取值逐值不变）。

**修法**：`window_minimum_for` 改成 `_pick(available, floor, comfortable, ratio)`
（先取"下限与舒适值之间的目标"，再用屏幕的九五成封顶）；
新增 `console_dialog_size_for`（同一套规则，「控制台」弹窗原来固定 860×560 ——
1366×768 笔记本在 150% 下只有 512 逻辑像素高，弹窗比屏幕还高，底部「关闭」按钮点不到）。
弹窗在 `open_console()` 里**装不下才收敛**，用户自己调过的尺寸不动。

用例：`test_window_minimum_never_exceeds_a_small_screen`、
`test_console_dialog_size_never_exceeds_a_small_screen`、
`test_open_console_resizes_itself_to_fit_the_screen`；
原来那条 `test_window_minimum_keeps_a_usable_floor` 把两条**互相冲突**的要求同时钉住了
（640×480 的屏幕上不可能既 ≥720×520 又 ≤ 屏幕），已改写为"屏幕装得下时才保留下限"。

### 连带修的测试方法问题：取色没算 devicePixelRatio

150% 下 `widget.grab()` 出来的是**物理像素**图（1.5 倍），而所有取色用例都在用逻辑坐标
`image.pixel(x, y)` —— 于是取到了别的地方（实测："脚本只读底"那一格取到了行号区的颜色，
三条用例假红）。新增 `tests/conftest.py::Grab`：按 `devicePixelRatioF()` 换算后再取色，
`test_theme.py` 与 `test_appearance.py` 的取色全部改走它。改完之后 150% 与 100% 两套
跑出来的结论一致 —— 这也是"像素级用例在高 DPI 下仍然可信"的前提。

### 其它 Windows 方向的核对（都做了，结论写在 packaging/build.md）

- **打包收集**：Linux 产物用**同一份 spec**，PyInstaller 分析表里 `wrap_row` / `selection_menu`
  都在（新模块都在包内，自动收集），模板库由 `BUILTIN_TEMPLATES` 在首次 `list()` 时写进用户数据
  目录 —— 打包产物不会出现空模板库；
- **CRLF**：`set_quote()` 显式把 CRLF 规范化成 `\n`（Qt 控件那条路本来就是 U+2029 → `\n`，
  但公开入口不能假设调用方经过控件），用例 `test_crlf_quote_is_normalized`；
- **打包脚本**：`build.bat`（纯 ASCII + CRLF）与 `build.sh` 共用同一份 spec、抽查同一组 Qt 插件，
  这两条都有契约用例守着；本次没有新增数据文件，两个脚本都不需要改；
- **手测清单**：`packaging/build.md` 新增 §6.2（B1~B9：控制台弹窗、右列页签、选中引用、
  接受并重跑、窄栏折行、150% 缩放），以及"高 DPI 形状怎么在没有 Windows 的机器上验"的说明。

### 测试

`QT_SCALE_FACTOR=1.5` 跑完整套：**466 passed / 2 skipped**（跳过的两条：需要真 opencode 凭据的
live 冒烟、以及本机测试屏装不下右列对话页的那条，后者跳过理由写在用例里）。
默认（100%）跑完整套：**466 passed / 2 skipped**。


### 附：顺手清掉的不可达平台代码（同一晚）

`ui/backdrop.py` 里还留着 `enable_translucent` / `disable_translucent` / `try_enable_blur` /
`_enable_windows_acrylic`（DWM）/ `_enable_kde_blur`（KWin），以及**重复定义了两遍**的
`erase_damage` —— 这是改自绘方案时的合并残留（文件中间那段注释写着"这里曾经有…"，
但函数本体还在下面）。产品里对它们的引用数是 0，也就是说：

- 它们是**Windows 专有、开发机上跑不到、也没有用例**的代码，正是"Windows 版本可能出问题"
  最典型的一类来源；
- 模块文档字符串还在描述旧方案（"拿不到模糊时不假装成功"、"Windows 走 DWM"），与现状不符。

处理：删掉这五个函数与重复定义，文档字符串改写成现状（两种效果都是界面自绘，窗口始终不透明，
并保留"为什么不再问系统要模糊"的实测原因）；`theme.py` 里两处过时说明同步改掉。
`test_ui_layer_keeps_its_platform_branches_in_one_place` 的豁免名单从两个文件**收紧到一个**
（只剩 `ui/acrylic.py` 的 Windows 壁纸探测）—— 变异验证：往 `ui/chat.py` 或 `ui/backdrop.py`
里塞一个 `sys.platform` 分支，这条用例立刻转红。

顺带修掉一条**脆弱的取色断言**：`test_theme.py` 里"主按钮浅底深字"与"引用条底色"用的是
**单个像素**，而那个像素正好在文字上 —— 别的用例改过全局字体之后采样点落进字形，
断言就红了（实测取到 `#b7b8ba` / `#9e9ea2`，也就是文字的颜色）。改成
`tests/conftest.py::Grab.dominant()`：取区域内**出现次数最多**的颜色（底色必然面积最大），
这类断言从此与字体度量无关。
